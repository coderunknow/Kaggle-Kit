# Kaggle-Kit v0.1.0-dev3

> The third prerelease. It makes the connection diagnosis truthful, gives the
> connection test and the chat one configuration, and adds a one-command
> Windows launcher. The Kaggle deployment, the pinned model, the request
> contract and the stored profile/conversation formats are unchanged.

## What changed since v0.1.0-dev2

### Connection diagnosis that matches the evidence

The connection test is now a six-stage sequence with an explicit state per
stage (`not run`, `running`, `ok`, `warning`, `failed`, `not applicable`):

| Stage | What it proves |
| --- | --- |
| Reachability | A server answered the request with an HTTP status. |
| Authentication | The endpoint accepted the API key (or the request without one). |
| Model list | `GET {base}/models` returned a readable list. |
| Usable model | The configured model is advertised, or the endpoint reported none. |
| Inference | A real `POST {base}/chat/completions` returned a non-empty answer. |
| Streaming | Checked separately by **Verify streaming support**; never implied. |

* `Connected` is shown only when the inference stage succeeded. A successful
  model list, a 200 status or a reachable socket never produces it.
* The stages keep the causes apart: no HTTP answer at all (network/timeout),
  401/403 (key), 404 (route or model), 400/422 (request), 5xx (server),
  inference accepted but empty, and unreadable responses. The code never
  infers a cause from a status code that was not observed.
* Streaming stays `not run` until a real `text/event-stream` probe returns
  content and a finish reason (or `[DONE]`). A connection test that only
  verified inference reports "streaming not verified".
* Every result names the tested endpoint, the value that was typed (when it
  was normalized), and the test time, and gives a next step for the confirmed
  cause.

### One connection, used by every surface

The audit found the root cause of the Settings/chat mismatch: the chat posted
to the raw `profile.baseUrl`, while the connection test and the settings cards
used a normalized URL. A profile that was saved as `https://host` therefore
tested `https://host/v1` but chatted with `https://host` — and the status badge
was derived from a test that could belong to a different URL, model or key.

The fix is a shared module (`shared/connection.ts`) that every consumer uses:

* **One resolution of the active profile** for the test, the chat request, the
  settings cards, the context bar, the sidebar footer and the header.
* **One normalization** (`normalizeBaseUrlDetailed`): a missing `/v1` is added,
  an existing `/v1` is never duplicated, a legitimate path prefix is kept.
* **Requested vs effective URL** are shown side by side in the editor and the
  profile card; the chat sends exactly the effective URL.
* **Fingerprint-bound status**: a stored result counts only while it matches
  the current URL, model, timeout and credential identity. Editing any of them
  drops the result (and the discovered models when the endpoint changed), so a
  green state can never survive a configuration change.
* **Draft isolation**: a test of unsaved values stays inside the editor. It is
  attached only when the saved configuration matches the tested one, and a
  failed test is stored as failed, never as healthy.
* **Same credential resolution** for the test and the chat, including the
  server secret store, the in-memory session key and the opt-in browser key.
* **Same error wording** in Settings and in the chat, because both use
  `describeErrorKind` and the same proxy error shape.

### One command on Windows

`scripts/start-windows.ps1` checks Node.js and npm, then delegates to
`tools/launcher.mjs`, which:

* verifies the project files and the Node requirement (`>=20.19`);
* installs missing dependencies with the lockfile (`npm ci`) when a build is
  needed and says that the npm registry is required;
* builds the client and the proxy only when their output is missing (an
  application bundle starts without `node_modules` and without the network);
* chooses the configured port, reports a conflict and moves to the next free
  port unless the port was passed explicitly;
* waits up to 45 seconds for `GET /api/health`, detects a backend that exited
  during start-up and prints the reason;
* opens the browser after readiness and prints the local URL;
* stops the backend on Ctrl+C and force-stops it after five seconds.

It requires no administrator rights and never reads, writes or prints an API
key. The wrapper and the launcher are tested on Linux; the PowerShell wrapper
itself is covered by static checks and was not executed on a real Windows
machine in this environment.

### Checking the real Kaggle endpoint

`tools/check-kaggle-connection.ps1` asks for the base URL and the API key
(hidden input, memory only), performs the model list request, a real
non-streaming inference request and a real streaming request, and prints a
sanitized JSON report with a masked URL. The key is never a parameter, never a
command line value and never part of the output.

## Verification

The automated checks of this release are listed in
`verification-report.json` and were executed by the release workflow:

- `npm run typecheck`, `npm run lint`, `npm test`
- `npm run build`, `npm run check:integration`
- `python3 -m unittest discover -s notebooks -p 'test_*.py'`
- `python3 -m unittest discover -s tools -p 'test_*.py'`

The regression suite covers the reported defects directly: the same effective
URL in Settings and the chat, no stale URL or key after a profile change, no
duplicated `/v1`, no success when inference fails, streaming not verified
without a successful probe, no key in an error body or the UI, and the launcher
handling missing Node/npm, missing dependencies, port conflicts and a backend
that does not become ready.

**Real Kaggle endpoint: NOT RUN for this release.** The environment that built
the release blocks outbound TLS, and the local check was deferred. No real
`/v1/models`, inference or streaming result is claimed here. A request that was
not executed is reported as **not run**, not as a success.

## Upgrading

Profiles, conversations, preferences and stored keys keep their formats. The
only visible change is that a profile whose stored test does not match its
current configuration now shows **Test needed** instead of a stale green
state. Run **Test connection** once after upgrading; the Kaggle model and the
notebook start-up configuration are unchanged.
